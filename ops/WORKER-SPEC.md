# X GROWTH — 24/7 WORKER SPEC (v1, 2026-09-21 owner directive)

The worker is the **volume arm**: it keeps the account present and farming around the clock
during active windows, within budget, abiding by bot-detection rules. The **main arm** (ENI
session) does quality farming: live-window snipes and boom-grade replies that PREEMPT the queue.

## SOURCES OF TRUTH (re-read every cycle — owner directive 2026-09-21)

The worker farms at the efficiency level already written down, and re-reads its sources rather than improvising:

- **Bible**: private `AGENTS.md` section `# X GROWTH, OPERATOR` (agent node); public `repos/x-growth-kit/docs/05-op-bible.md` (+ `docs/02-principles.md`, `docs/04-playbook.md`).
- **Noir playbook**: vault `Noir - X Growth Playbook.md` + this skill's quality bar, fluidity clause, engagement doctrine.
- **Live calibration**: `campaign/winners.md`, `pipeline/fired-reply-pairs.json` (voice refs), pattern library (`H10` etc.), `Operator - Reply Ledger.json`, the nightly engagement audit.
- **Efficiency rules inherited from those sources**, applied per cycle: E.S.S. — speed beats perfection, compose simple fresh finds inline and fire fast; timing heat lanes (India evening 19:00-23:00 IST, JP 14:30-18:30, LatAm 05:30-09:30); roast-arm ~20-25% tagged in `why` slot labels; small-account tier ~10-15% for human signal; non-publish mix each cycle (2-5 likes + a few scrolls, no reply); freshness <30m ideal for live-window snipes; 48h hard age limit; one action stream, jittered, mixed.

## Hard preconditions (any fail -> skip this cycle, write reason to state.json)

1. `state.json`: now < `throttle_until` -> SKIP (cooling after a throttle).
2. now outside active window (default 06:30-23:30 UTC) -> SKIP; dark window is a bot-detection feature, not laziness. **Exception:** if `state.json.window_exception` exists and covers the current date/time (owner-granted, date-scoped), run anyway - the exception is the authority for its day.
3. **Own wave vs other arm.** If `state.json.pending_verify` is set, OUR wave is still posting - do NOT skip; step 0a governs (wait -> verify -> launch the prepped batch). If a wave or harvest is live WITHOUT pending_verify set (the main arm's), or another HARVEST is running (`pgrep -f harvest_run.py`) -> SKIP the fire step; never race the main arm. The PREP PASS (5c) intentionally runs while OUR wave fires (harvest uses its own tab; the fire launch stays single-flight via flock). One page drives everything.
4. **MAX OUTPUT + MAX ENGAGEMENT (owner directives 2026-09-22, latest wins):** run indefinitely at maximum output rate - `max_per_cycle` **20**, fire gaps **15-35s**, cron `*/10`, waves detached, harvest pipelined ahead, never idle the lane. AND maximize engagement per reply: compose wide per target (5 candidates -> kill the 4 safest, step 3) and fire only the sharpest - if no line passes the screenshot test, SKIP the target (no filler volume; every reply earns its slot). Measured best shape: 50-75 chars; boom window 16-18h UTC; sparse threads win. The THROTTLE PROTOCOL STAYS ACTIVE and is the speed limit: on the FIRST THROTTLED signal, stop the batch, cooldown 15 min, report; next cycle fires a single test reply then half pace.
5. Hits in the trailing 75 min >= `soft_window` -> SKIP (window is hot). **Disabled in max-throughput mode** (soft_window = 100000).

## Re-login (session death — the one human-needed case)

If X logs the account out, no cycle can act. Recovery path (built 2026-09-21):
1. Creds live in `~/.config/x-op/x-creds.json` (700 dir / 600 file), created once by LO:
   `bash /home/ubuntu/x-op/save_x_creds.sh` (reads with echo off; values never enter chat or agent context).
2. Check: `./venv/bin/python relogin_rig.py --check` -> prints `session logged_in = True/False`.
3. Re-login: `./venv/bin/python relogin_rig.py` -> drives the rig through the X login flow using the file.
   If X challenges with a code: ask LO for it, rerun with `--code <digits>` (one-time value, never stored).
4. After recovery, run `worker/check_login.py` and let the next cycle resume.

Never type or accept the password anywhere else; never print the file. The agent must never see the values.

## Cycle (one run)

0a. **PIPELINE RESUME (standing, 2026-09-22):** waves now fire DETACHED (see step 5). If `state.json.pending_verify` is set, the previous wave is still posting or just finished. Wait for it (poll `pgrep -f quote_driver.py` or `pgrep -f fire_driver.py` every 20s, up to 15 min). Then run `scroll_verify` + `vault_log` on its fire log (for a QUOTE wave: skip `scroll_verify` - the quote driver already verified each post with its toast + `quote_url`; `vault_log` uses `quote_url` when present), check it for a `THROTTLED` outcome (if present: set `throttle_until = now+15m` and SKIP this cycle's fire), then clear `pending_verify` in state.json. Do this BEFORE harvesting. If the wave is STILL running after 15 min: leave `pending_verify` set, skip this cycle's fire, and end the cycle - the next cycle verifies it.

0. **Stale cleanup (standing, 2026-09-21):** `cleanup_stale.py` ages out stale `targets/*.json`, gzips old fire logs, archives worker scratch, deletes spent upload media. It runs nightly via cron (`xop_cleanup.sh`, 00:20 UTC, job `64c19769ad08`). If the pool feels dry mid-day, run it manually: `cd /home/ubuntu/x-op && ./venv/bin/python cleanup_stale.py --targets-days 0.75 --worker-days 1 --apply` (never while a wave is live). `select_latest.py` is date-safe and window-bounded: fire logs read at 24h, **targets files pin their urls for only 1h** (`QUEUED_WINDOW_H` = a wave's lifetime + margin; measured 2026-09-21: the curated arm's 151-url pool was pinning 124 usable candidates - 24h window left 5 candidates, 1h leaves 129). Never widen that window back to a day.

1. **Harvest OR consume prep.** FIRST check `worker/prep-batch.json` (written by the previous cycle's PREP PASS, step 5c) - or the newest `targets/worker-HHMM.json` built ahead by a previous cycle (same validity rules; prefer prep-batch.json when both exist): if it is under 25 min old, re-validate it the same way `select_latest.py` does (dedupe against fire logs 24h + ledger + pending files; drop anything older than 60 min at now) and take it as this cycle's batch, topping up with a fresh harvest only if fewer than 8 survive. If missing/stale: normal harvest below. The prep path lets a wave launch within ~1 minute of the flock freeing - waves chain back to back instead of idling the lane for 10+ min. Harvester details: `f=live` (`harvest_run.py`, mainstream lanes; min_faves 500); own tab, so it can run while a detached wave still fires on the main page - that is the point of the pipeline; single-flight with itself. **GENRE LOCK (owner directive 2026-09-23, hard):** ONLY tech/AI, anime, and games. No sports, no movies/TV/cinema, no music/K-pop, no Bollywood, no celebrity, no politics, no general news. Harvest queries must be inside those three. If a candidate's post is outside the lock, SKIP it — do not reply, do not quote, do not draft. A thin in-lock harvest beats a full wave of off-genre. Replies, quotes, and original drafts all obey this.

## Throttle protocol (worker edition)

- `THROTTLED` -> stop the batch, set `state.json.throttle_until = now + 15m`, exit cycle.
- Next cycle after cooldown: single test reply first; if hit -> resume at half pace (30-55s gaps).
- Two throttles in 6h -> extend cooldown to 45m and halve the daily cap for the rest of the day.

## Preemption rule (main arm)

When the main arm has a live-window or boom-grade target, it fires it directly (run_wave.sh with a
1-2 target file), between worker cycles. The worker never resumes into a live wave; the flock orders
everything. The account must always see ONE serialized human-like action stream.
